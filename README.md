# jjinmap

공공데이터로 장소를 검증하는 지도. 두 개의 모드를 가진다.

## 문제

맛집 지도는 이미 많다. 전부 같은 약점을 공유한다 — **평점과 리뷰는 살 수 있다.**
협찬 블로그, 대가성 리뷰, 부풀린 별점이 걸러지지 않은 채 "맛집"으로 올라온다.

## 접근

공공데이터에는 광고가 섞일 수 없다. 대신 평점도 리뷰도 없다.
그래서 인기를 직접 묻는 대신, **돈으로 살 수 없는 신호**로 대신한다.

모드는 두 개이고, 서로 다른 API를 문다. 하나의 점수로 섞지 않는다.

| | **찐 모드** | **핫플 모드** |
|---|---|---|
| 질문 | 오래 살아남았는가 | 지금 뜨는가 |
| 신호 | 생존기간 (인허가일자 → 폐업일자) | 실시간 결제금액·건수 |
| 출처 | LOCALDATA 지방행정인허가 | 서울 열린데이터광장 실시간 상권현황 (신한카드) |
| 해상도 | **개별 가게** (핀) | **상권 120곳** (폴리곤/히트맵) |
| 갱신 | 일 단위 | 10분 (가맹점수만 월 단위) |

해상도가 다르므로 signal provider 인터페이스는 `granularity`를 갖는다.

## 검증된 사실 (factchk, 2026-08-27)

- **LOCALDATA**: 인허가일자·폐업일자·영업상태 제공 확인 → 생존기간 지표 성립
- **좌표계 함정**: LOCALDATA는 좌표를 `EPSG:2097`로 **표기하지만 실제는 `EPSG:5174`**.
  두 좌표계는 원점 경도에 `0.0028902777778` 보정값 유무만 다르며, 라벨대로 2097로 변환하면
  전 지점이 일정하게 어긋난다. **5174로 읽고 WGS84(4326)로 변환할 것.**
- **소상공인 상가(상권)정보 API**: 경도·위도를 **직접** 제공 → 변환 불필요.
  변환 파이프라인이 필요한 건 LOCALDATA 계열뿐이다.
- **실시간 상권현황**: 신한카드 결제 데이터 10분 단위 집계. 15종 업종별 결제금액·건수,
  성별·연령대별 소비 비중, 개인/법인 구분, 혼잡도 4단계(한산/보통/바쁨/분주). 무료.
- **호출제한**: 개발계정 1,000건/일 · 운영계정 100,000건/일
- **갱신주기**: 실시간 인구 5분 / 실시간 상권 10분

## 실호출로 확정한 것 (2026-08-27, 실제 API 응답)

- **장소 수 = 120곳.** `POI001`~`POI130` 범위에 결번 10개
  (POI022, 028, 057, 062, 065, 069, 075, 097, 099, 113). 상한(130) ≠ 개수(120).
  전체 목록은 [`data/seoul_areas.json`](data/seoul_areas.json).
- **`LIVE_CMRCL_STTS` 실재 확인.** 신한카드 결제 데이터가 `citydata` 응답에 그대로 들어있다:
  `AREA_SH_PAYMENT_CNT`(건수), `AREA_SH_PAYMENT_AMT_MIN/MAX`(금액 구간),
  업종별 `CMRCL_RSB[]`(대/중분류, 결제수준 4단계, 가맹점수 `RSB_MCT_CNT`).
  단 `RSB_MCT_TIME`은 월 단위(예: 202607) — **가맹점 수는 실시간이 아니다.**
- **소상공인 API는 경도·위도를 직접 준다** (`lon`/`lat`, WGS84). 변환 불필요.
  강남역 반경 500m에 6,617건. 기준년월 `stdrYm=202606`.

## 설계를 바꾸는 제약: 두 소스는 조인 키가 없다

소상공인 상가정보의 컬럼 39개에 **시간 관련 필드가 하나도 없다** (개업일·폐업일·등록일 전부 없음).
"지금 영업 중인 가게"의 스냅샷일 뿐 시간축이 없다.

따라서 **찐 모드(생존기간)는 LOCALDATA 없이 성립하지 않는다.** 그런데:

| | 소상공인 상가정보 | LOCALDATA 인허가 |
|---|---|---|
| 주는 것 | 정확한 좌표, 정제된 업종분류 | 인허가일자, 폐업일자, 영업상태 |
| 없는 것 | **시간축 전부** | 위경도 (TM만, 라벨도 틀림) |
| 식별자 | 상가업소번호 | 인허가관리번호 |

두 식별자는 서로 무관하다. **공통 키가 없으므로 상호명+주소 기반 매칭이 필요하고,
이 매칭 정확도가 찐 모드의 품질 상한이다.** 이게 이 프로젝트의 핵심 기술 난제다.

## 미해결 (확정 전 코드 금지)

- [ ] **매칭 전략** — 상호명+도로명주소 정규화 후 매칭. 정확도 측정 방법과 목표치를 게이트로 정할 것.
- [ ] **평점·리뷰 부재** — 확인된 필드 목록엔 없으나 "없다"고 명시한 1차 문서 미확보. 단정 보류.
- [ ] **해외 IP 차단** — localdata.go.kr 직접 접속이 ECONNREFUSED로 거부됨.
      배포·CI를 해외 리전에 올리면 수집이 통째로 막힌다. 국내 리전 또는 국내 경유 수집 필요.
- [ ] 지역 범위 (핫플은 사실상 서울 한정, 찐은 전국 가능 — 범위가 모드마다 다름)
- [ ] 웹 / 앱, 지도 렌더러 선택
- [ ] `/re0-plan` 으로 구현 계획 착수
