# jjinmap

공공데이터로 장소를 보는 지도. 광고가 섞이지 않은 신호만 쓴다.

> 상태: **설계 중, 코드 없음.** 스택·화면·렌더러 미정. 아래 "미해결"이 확정되기 전에는 코드를 쓰지 않는다.
>
> **2026-08-27 — 재범위했다.** 영업 지속기간이 품질의 대리 지표로 성립하는지를 측정했고
> (게이트 G0) **불합격**이다 — 미쉐린 서울 빕구르망 28곳의 백분위 중앙값 **47.1**, 무작위(50)
> 보다 낮다. 그 뒤 배지(미쉐린·블루리본) 레이어도 **제외**했다(상표·재배포 노출, 유료 게재 논란).
>
> 남은 설계는 **기존 API가 실제로 재는 것을 그 이름으로 표시하는 지도**다 — 나이와 결제.
> 대리 지표를 쓰지 않으므로 정답셋·사전등록·벤치마크가 **필요 없다.**

## 문제

맛집 지도는 이미 많다. 전부 같은 약점을 공유한다 — **평점과 리뷰는 살 수 있다.**
협찬 블로그, 대가성 리뷰, 부풀린 별점이 걸러지지 않은 채 "맛집"으로 올라온다.

## 접근

공공데이터에는 광고가 섞일 수 없다. 대신 평점·리뷰 같은 인기 지표도 없다.

한 번은 그 공백을 **대리 지표**로 메우려 했다 — 오래 살아남았으면 좋은 집일 것이다.
측정해보니 아니었다(아래 [G0](#g0--영업-지속기간은-품질-신호가-아니다-2026-08-27-측정-완료)).
그래서 방향을 바꿨다:

> **대리 지표를 쓰지 않는다. 데이터가 실제로 재는 것을, 그 이름으로 표시한다.**

지속기간은 품질이 아니라 **나이**를 잰다. 그러면 "1968년부터 영업 중"은 대리 지표가 아니라
**사실**이고, 사실은 정답셋으로 채점할 대상이 아니다. 순위를 매기지 않으므로 임계값도,
정규화도, 벤치마크도 필요 없다 — 축을 보여주고 사용자가 직접 고른다.

같은 규칙이 핫플 모드에도 적용된다. `AREA_SH_PAYMENT_*`의 `SH`는 신한이다.
그러므로 그 숫자는 "결제 건수"가 아니라 **"신한카드 결제 건수"** 이고, 그렇게 표시한다.

*"광고가 섞이지 않는다"는 전제는 그대로 살아 있다 — 인허가 대장도 카드 결제도
광고비를 써서 그 숫자를 만들 수 없다. 내려놓은 것은 **그 숫자가 품질을 뜻한다**는 주장이다.*

## 두 모드

서로 다른 API를 물고, 하나의 점수로 섞지 않는다.

| | **나이 축** (구 "찐 모드") | **핫플 모드** |
|---|---|---|
| 표시하는 것 | 이 가게가 몇 년째인가 | 이 장소가 지금 얼마나 붐비는가 |
| 신호 | **영업 지속기간** = 인허가일자 → 오늘 | **신한카드** 결제 건수·금액구간 |
| **주장의 강도** | 사실 (대장 기준). **품질 주장 없음** | 사실 (한 카드사 기준). 시장 전체 아님 |
| 폐업 데이터 용도 | 지도에서 제외하는 필터 (표시 대상 아님) | — |
| 출처 | LOCALDATA 지방행정인허가 (서울 미러) | 서울 열린데이터광장 `citydata` |
| 해상도 | 개별 가게 (핀), 영업중 120,326곳 | 서울 주요 장소 120곳 (폴리곤/히트맵) |
| 갱신 | 일 단위 | 원본 10분, **실제 가능 3시간** (아래 쿼터 참고) |
| 범위 | **서울** (v0) | **서울** |

해상도가 다르므로 signal provider 인터페이스는 `granularity`(`store` \| `area`)를 갖는다.
**두 모드를 하나의 점수로 섞을 이유는 이제 없다** — 둘 다 서로 다른 사실이므로 별개 레이어로 둔다.
토글/탭/레이어 중 무엇으로 할지는 미정(미해결 8번).

배지(미쉐린·블루리본) 레이어는 **제외했다** — 아래 "닫힌 항목" 참고.

## 확인된 사실

`실호출` = 실제 API 응답으로 확인. `문서` = 공식 문서·1차 자료로만 확인. (2026-08-27)

### LOCALDATA 지방행정인허가

- `문서` 인허가일자·폐업일자·영업상태 제공 → 지속기간 지표 성립
- `문서` **좌표계 함정**: 좌표를 `EPSG:2097`로 표기하지만 실제는 `EPSG:5174`.
  두 좌표계는 원점 경도의 `0.0028902777778` 보정값 유무만 다르다.
  라벨대로 2097로 변환하면 전 지점이 일정하게 어긋난다. **5174로 읽고 WGS84(4326)로 변환.**
  단 어긋나는 **크기(m)를 아직 측정하지 않았다** — 회귀 테스트를 쓰려면 이 수치가 필요하다.
- `실호출` **서울 한정 경로 확보.** `localdata.go.kr`은 여전히 안 닿지만, 서울 열린데이터광장이
  같은 데이터를 자기 호스트로 미러링한다: `openapi.seoul.go.kr:8088` → `LOCALDATA_072404`(일반음식점).
  **536,710건 전량 수신 완료.** 39필드에 `APVPERMYMD`(인허가일자)·`DCBYMD`(폐업일자)·
  `TRDSTATENM`(영업상태)·`UPTAENM`(업태)·`X`/`Y`(TM 좌표)·`BPLCNM`·주소가 **한 레코드에 다 있다.**
  1콜 1,000행이라 전량 537콜(개발계정 일일 쿼터의 54%). **전국은 여전히 미해결**(미해결 12번).
- `실호출` **서울 일반음식점 실측(2026-08-27, 전수).** 영업중 **120,326** / 폐업 416,379 —
  **폐업률 77.6%**. 영업기간 중앙값 **8.1년**, p95 33.2년, 최대 115.2년.
- `실호출` **인허가일자는 실제 영업 시작을 과소평가한다.** 같은 번지·같은 상호에 더 이른
  인허가 기록이 있는 영업중 업소가 **3,388곳(2.8%)**, 숨은 연차 중앙값 4.9년·최대 46.6년,
  20년 이상 과소평가 341곳. **이 2.8%는 바닥값이다** — 상호 변경이나 이전은 이 방법으로 안 잡힌다.
  실제 비율은 더 높고, 얼마나 높은지는 모른다 (미해결 4번).

### G0 — 영업 지속기간은 품질 신호가 아니다 (2026-08-27, 측정 완료)

`/hate`가 짚은 하중 가정을 측정했다. 기존 게이트들은 지속기간을 *계산할 수 있는가*만 물었고
*무엇을 뜻하는가*는 묻지 않았다. 합격선은 측정 전에 고정했다([`PREREG.md`](PREREG.md) 해시).

**정답셋**: 미쉐린 가이드 서울 빕구르망 51곳(2026 셀렉션). 지속기간과 독립적으로 선정되고,
1인당 4만5천원 이하 기준이라 고급 편향이 적다. `노포`·`백년가게` 계열은 **업력으로 선발된
목록이라 신호의 복사본**이므로 명시적으로 배제했다.

| | 값 | 합격선 |
|---|---|---|
| 표본 N (단일 완전일치) | 28 | ≥ 25 ✅ |
| 백분위 중앙값 | **47.1** | ≥ 65 ❌ |
| 무작위 기대값 | 50 | — |

**판정: 불합격.** 민감도 분석에서도 뒤집히지 않는다 — 모호 8곳을 전부 최댓값으로 넣어도 55.2,
미매칭 15곳을 **전부 백분위 100**으로 놓는 물리적 상한에서만 69.0이다. 실제로 그 15곳은
대부분 2019~2023년 개업이라 낮은 쪽에 몰린다.

**신호가 무엇을 놓치는가.** 매칭된 28곳은 두 덩어리로 갈린다 — 백분위 50 이하 15곳은
2~8년 된 신생(옥동식 1.3, 소바키리 스즈 11.2, 안덕 19.3, 오일제 27.1…), 83 이상 7곳은
30년+ 노포(필동면옥 84.5, 우래옥 88.6, 옥돌현옥 94.9, 임병주 산동칼국수 95.6).
**미쉐린은 노포와 신생을 모두 고르는데, 지속기간은 그 절반만 본다.**
신규 좋은 가게는 정의상 최하위이므로 구조적으로 보이지 않는다.

재현: `python3 analysis/g0_tenure.py && python3 analysis/g0_judgment_A.py`

### 소상공인시장진흥공단 상가(상권)정보

- `실호출` 경도·위도를 `lon`/`lat`(WGS84)로 **직접** 제공 → 좌표 변환 불필요
- `실호출` 강남역 반경 500m에 6,617건. 기준년월 `stdrYm=202606`
- `실호출` 컬럼 39개에 **시간 관련 필드가 전무** (개업·폐업·등록일 없음)

### 서울 열린데이터광장 `citydata`

- `실호출` **장소 120곳.** `POI001`~`POI130` 중 결번 10개
  (POI022, 028, 057, 062, 065, 069, 075, 097, 099, 113). 상한(130) ≠ 개수(120).
  전체 목록 [`data/seoul_areas.json`](data/seoul_areas.json)
- `실호출` **이 120곳은 상권이 아니다.** 역·교통 46, 공원·한강 28, 관광특구 7, 고궁 4, 기타 35.
  한강공원과 경복궁이 포함된다. "상권 120곳"으로 부르면 핫플 모드의 전제가 틀어진다.
- `실호출` `LIVE_CMRCL_STTS`에 신한카드 결제 데이터가 그대로 들어온다:
  `AREA_SH_PAYMENT_CNT`(건수), `AREA_SH_PAYMENT_AMT_MIN/MAX`, 업종별 `CMRCL_RSB[]`,
  `AREA_CMRCL_LVL`(상권 활성도, 관측값 `바쁜`). **금액은 스칼라가 아니라 구간이다** —
  랭킹하려면 규칙이 필요하다. 인구 혼잡도(`AREA_CONGEST_LVL`)는 여기가 아니라 아래 인구 블록에 있다.
- `실호출` `RSB_MCT_TIME`은 월 단위(예: 202607) — **가맹점 수는 실시간이 아니다**
- `실호출` **결제 업종 대분류는 음식·음료 / 유통 / 의료 셋뿐이다.** 강남역 기준 `CMRCL_RSB[]`
  중분류 7개(한식, 제과/커피/패스트푸드, 기타요식, 할인점/슈퍼마켓, 편의점, 병원, 약국)의
  건수 합이 `AREA_SH_PAYMENT_CNT`와 **정확히 일치**한다 → 상위 N개를 자른 게 아니라 이게 전부다.
  두 가지가 따라온다. (1) **숙박·문화·관광 업종이 없다** — 결제 신호로는 관광지 소비를 볼 수 없다.
  (2) 병원 34건이 제과/커피 36건과 맞먹는다 — 결제를 그대로 쓰면 **맛집 신호에 병원·약국·편의점이
  섞여 들어온다.** 걸러내는 규칙이 필요하다.
  단 이는 장소 1곳·시각 1개 관측이며, 장소·시간대별로 대분류가 달라지는지는 미확인.
- `실호출` `LIVE_PPLTN_STTS`에 인구 신호가 통째로 들어온다: `AREA_CONGEST_LVL`(4단계),
  `AREA_PPLTN_MIN/MAX`, 성별 비율, **연령 8구간**(`PPLTN_RATE_0`~`_70`),
  `RESNT_PPLTN_RATE`/`NON_RESNT_PPLTN_RATE`(상주/비상주), 그리고 `FCST_PPLTN` —
  **시간 단위 인구 예보**. 국적·외국인 필드는 응답 전체에 **없다.**
- `실호출` 응답 최상위 블록은 **17개**. 핫플 모드가 쓰는 건 `LIVE_CMRCL_STTS` 하나뿐이고,
  나머지 16개는 **같은 호출에 딸려온다** — 추가 쿼터 없이 이미 손에 있다(미해결 11번 — 손대지 않는다).
- `문서` 한 번에 1개 장소씩만 호출 가능. 인구 5분 / 상권 10분 갱신

### 호출 쿼터 — 10분 갱신은 개발계정으로 불가능

개발계정 1,000건/일, 운영계정 100,000건/일. 그런데 장소당 1콜이므로:

```
120곳 × 6회/시 × 24시간 = 17,280건/일   →  개발계정 한도의 17.3배
개발계정으로 가능한 전 장소 갱신 = 하루 8회 (약 3시간 간격)
```

**운영계정 승인 없이는 "실시간 핫플"이 성립하지 않는다.** 승인 전까지는 3시간 간격이거나,
장소를 추려야 한다.

## 조인 문제는 사라졌다 (소상공인 API 미사용)

두 소스에 공통 키가 없다는 제약이 오래 설계를 지배했다 — 상가업소번호와 인허가관리번호는
서로 무관해서, 합치려면 상호명+주소 매칭이 필요하고 그 정확도가 품질의 상한이 됐다.

**합치지 않기로 했다.** LOCALDATA 한 레코드에 좌표(`X`/`Y`, 5174로 읽음)·업태(`UPTAENM`)·
시간축(`APVPERMYMD`)·상호·주소가 **전부 들어 있다.** 소상공인 상가정보가 추가로 주는 것은
"이미 있는 것의 다른 판본"뿐이고, 대신 시간축이 없다.

따라 닫히는 것: 매칭 평가 설계, 매칭 정확도 상한, 두 소스의 기준시점 정합.
**단 조건부다** — 나중에 LOCALDATA 밖 필드를 요구하는 설계가 나오면 이 결정은 다시 열린다.

(한 동 ≈ 283곳)에 **0.12곳**이라 필터가 아니라 북마크 레이어다. 셀렉션 전체 200곳 가정 0.17%,
블루리본 서울 1,500곳 후한 가정으로도 1.25%.
(b) **상표·재배포** — 로고는 상표이고 목록에도 권리가 있을 수 있다. 미쉐린은 자기 sitemap까지
CloudFront WAF로 막는다(자동 수집 불가, 사람이 브라우저로 복사하는 것이 유일 경로).
(c) **블루리본은 유료 게재 논란이 있다** — "광고로 살 수 없는 신호"라는, 재범위 뒤에도
**유일하게 살아남은 전제**를 정면으로 건드린다. 미쉐린 대신 블루리본을 넣는 건 깨끗한 블로커를
지저분한 블로커로 바꾸는 교환이다.
→ **단, 미쉐린 28곳 백분위 표를 내부 분석에 쓰는 것은 별개다.** 법적 노출은 **표시·재배포**에서
오지 오프라인 검증에서 오지 않는다. `analysis/g0_ranked.jsonl`은 그대로 둔다.

### 살아 있는 항목 — 순서가 곧 계약이다

1. [ ] **이용약관 — 이것이 킬 게이트다.** LOCALDATA(서울 미러)의 재배포·상업적 이용 범위가
   막히면 나이 축이 죽고, 신한카드 파생 결제데이터가 막히면 핫플 모드가 죽는다. 둘 다 막히면
   프로젝트가 죽는다. **불합격이 나머지 전부를 무의미하게 만드는 유일한 항목이므로 첫 자리다.**
   비용은 두 포털 약관 읽기 — 코드 0줄, 쿼터 0. `추정`
2. [ ] **`AREA_SH_PAYMENT_*`가 신한 단독인가, 보정된 추정 시장값인가** — `SH`=신한이므로
   지금 표기대로면 그 숫자는 **한 카드사 표본**이다. 카드사 점유율은 지역·업종·연령대별로
   균일하지 않으므로, 단독값이라면 장소 간 비교(강남역 vs 홍대)가 그만큼 왜곡된다.
   보정 추정치라면 이 우려는 사라진다. **필드 이름만으로는 구분 불가.**
   비용은 보도자료·API 명세 한 페이지. 답에 따라 표기 문구가 갈린다. `추정`
3. [ ] **좌표계 어긋남의 크기(m)** — 이제 진짜로 핀 12만 개를 찍으므로 되살아났다.
   `EPSG:2097` 라벨 / `EPSG:5174` 실제의 차이를 **미터로 잰 적이 없고**, 유일한 근거가
   개인 블로그 1건이다. 기준점 몇 개 대조하면 끝난다. `2차자료`
4. [ ] **인허가일자 과소평가 → 표기 문구** — 랭킹일 땐 안 아팠는데 **연도를 화면에 적으면
   틀린 값이 보인다.** 같은 자리·같은 이름 기준으로만 2.8%가 과소평가(중앙값 4.9년, 최대 46.6년)
   이고 이건 **바닥값**이다 — 상호 변경·이전은 못 잡으니 실제는 더 높고 얼마나 높은지 모른다.
   표기로 흡수한다: "1968년 인허가" 또는 "최소 57년"처럼 **대장 기준임을 드러내는** 문구.
   1차 문서(영업자 지위승계 조항) 확인은 여전히 남아 있다. `실호출` + `추정`
5. [ ] **결제금액 구간 랭킹 규칙** — MIN/MAX 구간으로 순위를 매기는 방법. `실호출`
6. [ ] **결제에 병원·약국·편의점이 섞인다** — 강남역 기준 병원 34건이 제과/커피 36건과 맞먹는다.
   음식 관련만 거르는 규칙이 필요하다. 대분류가 장소·시간대별로 달라지는지는 미확인. `실호출`
7. [ ] **프로젝트 이름** — "찐"은 품질 주장을 담은 단어인데 그 주장을 내려놨다. 나이 축을
   "찐맛집"이라 부르면 G0이 반증한 문장을 다시 하는 것이다. 이름을 바꾸든, "찐"의 뜻을
   재정의해 문서에 못 박든 결정이 필요하다. **코드 쓰기 전에.**
8. [ ] **웹/앱, 지도 렌더러, 두 모드의 화면 배치** — store 핀과 area 폴리곤은 해상도가 다르므로
   같은 필터에 못 들어간다. 별개 레이어로 두는 것까지는 정해졌고, 토글/탭/동시표시는 미정.
9. [ ] **저장·수집 구조** — 서울 한정이면 53만 행. 저장소·수집 잡·스케줄러 미정.
10. [ ] **데이터 시점 불일치** — 가맹점수 `202607`(월 단위), 결제 실시간, 인허가 일 단위.
    묵은 명부 위의 "실시간"을 어떻게 표기할 것인가. `실호출`
11. [ ] **미사용 데이터 — 응답의 17분의 1만 쓴다.** `citydata` 최상위 17블록 중 쓰는 건
    `LIVE_CMRCL_STTS` 하나다. 안 쓰는 것: 인구 전체(혼잡도, 인구수, 성별, 연령 8구간,
    상주/비상주, **시간 단위 예보**), 결제 쪽 성별·연령·개인/법인 비중, 도로·주차·지하철·
    버스·따릉이·날씨·충전소·행사. **전부 추가 쿼터 없이 이미 온다 — 그래서 유혹이다.**
    ⚠️ RETRO가 이름 붙인 `소스→주장 역류`의 다음 판이다. **무엇을 주장할지 정하기 전까지
    16블록은 자산이 아니다.** 손대지 않는다. `실호출`
12. [ ] **전국 확장 — v0 범위 밖.** 나이 축은 원리상 전국 가능하지만 경로가 없다.
    `www.localdata.go.kr`은 443 침묵 타임아웃(20s)·80 즉시 거부, `openapi.localdata.go.kr`은
    **DNS A 레코드 자체가 없다**(차단이 아니라 존재하지 않는 호스트명). 반면
    `openapi.seoul.go.kr:8088`은 200, `apis.data.go.kr`은 400. 남은 갈래: (a) 국내에서도 같은지,
    (b) `apis.data.go.kr`이 지방행정인허가를 서빙하는지. 더하여 **5174는 중부원점 한 존이므로**
    전국을 하려면 존 처리가 필요하다. `실호출`

### 무엇이 바뀌었나 (한 문단)

품질 주장을 내려놨다. 지속기간은 **나이**를 재고, 나이는 사실이며, 사실은 검증할 대상이 아니다.
그래서 타깃 정의·정답셋 수집·사전등록·벤치마크가 **통째로 필요 없어졌다** — 지난 사이클을
하루 잡아먹은 기계 전부다. 대신 살아남는 전제는 하나뿐이다: **"이 숫자들은 광고비로 만들 수 없다."**
그 전제가 유효한지는 데이터가 아니라 **약관**이 정한다. 그래서 약관이 1번이다.
